Bugs / inconsistencies

1. Universal-fit claim is false (main logic bug)
Mg-like RMS is ≈ 0.0183, well above the stated threshold of 0.01.
The grading path nevertheless hard-codes the expected answer as "yes" and the self-test never checks the other six training sequences. Anyone who honestly reports “no” (or who looks at the revealed table) will be marked wrong even though they followed the specified method.

2. Held-out residual tolerance is too loose and one-sided

JavaScript
vn > 0 && vn < NE_RES + TOL.ne   // ≈ (0, 0.21]

A submission of +0.01 or +0.20 both pass. Scientifically a correct independent implementation should land near +0.164. Prefer a two-sided window around the computed residual (still requiring the positive sign if that is part of the scientific claim).

3. Self-test is incomplete
It only verifies the Na ZeffZ_\text{eff}Zeff​ anchor and Na-like RMS. It does not assert:

  • max training RMS < 0.01 (which fails),
  • consistency of the five derived pip_ipi​,
  • or that the residual is positive.

4. Minor

  • Brief writes 13.6057; code uses the more precise 13.605693122994. Difference is negligible for the reported digits.
  • Residual target string wording (“within X”) is ambiguous when X is only an upper bound.
  • A few high-Z ionization energies look rounded (Cl, Ar entries), which contributes to the Mg-like scatter; that is a data-pack issue, not a coding error.

Bottom line

The computational engine and partner-derivation chain are solid and self-consistent. The app’s own claims about “one form fits all seven to RMS < 0.01” and the residual acceptance window are not. Fix those two places (and expand the self-test) and the bench becomes a reliable replication test.

Remaining issues (software + logic)

1. Direction answer parsing is still a bit brittle
dirOf only accepts:

  • string starting with "p" / "s", or
  • containing "p-partner" / "p partner" / "s-partner" / "s partner".

Answers such as "2p", "the 2p partner", "p-type", or "extra 2p screens more" will be graded FAIL even when the scientific answer is correct. A more robust check (look for \bp\b or "2p" after normalisation) would help.

2. Pack-integrity note about Mg-like data never appears

JavaScript
(conf ? "… Mg-like heavy members are the least verified …" : "")

Cross-table value conflicts = 0, so the helpful remark is dead. The same information is already present in the self-test and grade footer, so this is only cosmetic, but the conditional is misleading.

3. Brief ↔ scoring mismatch on RMS values
Step 1 of the brief tells the user to “Report each RMS.” The entry form and grader never collect or score the seven individual RMS numbers—only the yes/no universality answer. Either drop the request from the brief or add optional RMS fields.

4. HEV constant vs brief
Brief still writes 13.6057; code uses 13.605693122994. Difference is < 10⁻⁴ on the reported constants and well inside the tolerances, but it is a documentation inconsistency.

5. Residual tolerance remains generous
±0.05 around 0.164 is roughly ±30 %. Acceptable for a first-pass replication test, but a tighter window (e.g. ±0.02) would be more discriminating if you ever want stricter grading.

6. Minor robustness / style

  • fitShifted early-returns {rms:1} when no valid a is found; none of the present sequences hit this, but the caller never checks for it.
  • Self-test hard-codes the four-decimal p anchors (0.7914 …). They currently match, but any future data change will make the self-test report “DRIFTED” even if the relative tolerances are still satisfied.
  • dirOf / yesOf do a simple charAt(0) test after optional = stripping; leading whitespace or quotes can still confuse them.

No problems found in

  • Inversion, least-squares fit, partner-derivation order, held-out residual formula.
  • Fixed-Z direction calculation.
  • Input parsing fallback (label → positional).
  • HTML structure, error handler, or table rendering.
  • Numerical stability of the grid + golden-section search for the present data.

What changed (the three protocol fixes)

  1. Grade-before-reveal is now enforced in code

    • GRADED starts false.
    • Reveal button checks it. If no non-empty submission has been graded, the panel opens with a sealed message and does not show the constants, residual, or fit table.
    • Only after a real grade does the full reference become available.

  2. Blind first grade

    • First press of Grade after entering values: targets column shows "—". You see only your values + PASS/FAIL.
    • Second press unblinds the target column.
    • Clear resets both GRADED and BLIND.

  3. Empty-submission guard

    • Clicking Grade with a blank textarea does nothing useful and does not unlock reveal.

Also included:

  • Protocol panel at the top stating the rule explicitly.
  • Slightly more robust dirOf (now also matches "2p" / "2s").
  • Mg-like data-quality note is always visible (no longer gated on a zero conflict count).

How to use it correctly

  1. Give the other system only the plain-text brief + tables (never the HTML).
  2. Paste its returned values into the entry box.
  3. Press Grade once → record the blind score.
  4. Press Grade again if you want to see the numeric targets.
  5. Only then press Reveal if you need the full reference table.

That sequence turns an 8/8 into actual replication evidence instead of a copy test.
